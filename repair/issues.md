# 完整问题清单

本文行号和“当前流程”描述对应 [修复前审查基线](./README.md)，后续修改后可能变化。`后端/` 表示 `/mnt/data/Mi_Power_Monitor/`；`KDE/` 表示 `/mnt/data/Mi_Power_Monitor_KDE/`。每项已修复状态和实测范围见文末“本轮修复结果”。

## R01：CPU 功耗未使用真实采样时长

**优先级：P1。审查基线状态：待修复；已隔离复现。**

定位：`KDE/backend/read-sensors.sh:25`、`:39`。

当前流程读取能量计数器，执行 `sleep 1`，再次读取后将能量差除以 `1000000`。这个除法只完成微焦耳到焦耳的换算；要得到瓦特，还必须除以实际经过的秒数。代码隐含假设两次读取恰好相隔一秒。

触发条件包括 CPU 调度延迟、系统负载高、多 Package 顺序读取，以及休眠恢复。实际时间超过一秒时，当前算法会高估平均功率。计数器在休眠后的行为还取决于硬件，不能简单把所有负差值都解释成一次正常回绕。

复现时仅将临时脚本的 sysfs 路径指向模拟目录，并让模拟 `sleep` 实际等待两秒。能量从 1,000,000 增至 41,000,000 微焦耳，采样命令耗时约 2.02 秒，却输出 CPU 40.0W；对应的平均功率应约为 20W。

修复建议：使用单调时钟记录采样时间，计算 `Δenergy_uj / 1_000_000 / Δseconds`。多 Package 需要明确各自时间窗口或采用足够接近的统一窗口。对非正时间差、明显超长窗口、计数器重置和无法可靠判断的回绕返回不可用。不要依赖系统墙上时钟，因为校时会影响时间差。

验收：同样的 20W 模拟输入在 0.5、1、2 秒窗口下结果均接近 20W；额外调度延迟不再被解释为功率升高；异常窗口不会产生离谱峰值。休眠恢复后的第一批数据应有明确的丢弃或重新建立基线策略。

## R02：CPU 统计混入非 Package 的 RAPL 域

**优先级：P1。审查基线状态：待修复；已隔离复现，实际硬件覆盖待补。**

定位：`KDE/backend/read-sensors.sh:8`。

当前只用目录名称中的 `rapl:[0-9]+` 筛选顶层域，并没有读取该域的 `name`。顶层域不一定都是 CPU Package；存在平台级 `psys` 域的系统可能被同时统计，从而使平台能量与 Package 能量混合、重叠。

隔离输入设置 `intel-rapl:0/name=package-0`、功耗 20W，`intel-rapl:1/name=psys`、功耗 80W，脚本输出 CPU 100.0W。这个测试确认了代码会忽略域名称；不表示当前机器具有 psys 域。

修复建议：读取域的 `name`，明确筛选 CPU Package，并按实际内核接口验证 Intel/AMD 的可支持命名。多插槽系统对所有有效 Package 求和；不能将 core、uncore、DRAM 或 psys 与 Package 重复叠加。未知域应该跳过并保留可诊断信息。

验收：Package 20W 加 psys 80W 时 CPU 仍为 20W；两个 Package 各 20W、30W 时为 50W；添加子域不改变结果；没有可识别 Package 时返回不可用。

## R03：采样失败被显示为零功耗或部分总和

**优先级：P1。审查基线状态：待修复；零值误报已隔离复现。**

定位：`KDE/backend/read-sensors.sh:26`、`:28`、`:39`。

`total_delta` 初始化为零。第二次读取失败或不是整数时直接 `continue`，结束后仍输出累计值，没有记录本轮成功采集了几个 Package。全部第二次读取失败时会输出 0W；部分失败时会输出剩余 Package 的总和。

复现输入第一次为有效数字，第二次改成 `invalid`，输出 `cpu_power:0.0`。前端把这个值视为正常可用，因此无法区分真实空闲功耗和采集失败。

修复建议：记录发现的 Package、预期参与计算的 Package 和成功样本。至少全部失败必须返回 `null`；对于部分失败，应明确“CPU 总功耗必须完整”的策略，推荐返回不可用，避免静默低估。首次读取即因权限失败而被跳过的 Package 同样需要纳入完整性判断。

验收：真实能量差为零时返回数值零；第一次/第二次读取失败、空内容、非法内容时返回不可用；两 Package 中任意一个失败不能冒充完整总功耗。QML 应显示 `--W`。

## R04：串行采集导致刷新变慢和时间错位

**优先级：P1。审查基线状态：待修复；串行耗时已隔离复现。**

定位：`KDE/backend/read-readings.py:46`；`KDE/package/contents/ui/main.qml` 的 DataSource `interval: 1000`。

采集器先等待 CPU/GPU 脚本结束，再执行插座后端。CPU 脚本内部先等待一秒，再查询 GPU。最终同时替换三个标签只能保证同一帧显示，不能保证采样时间一致，更不能保证一秒内完成采集。

模拟传感器命令耗时一秒、插座命令耗时两秒，整轮约 3.03 秒后才输出 JSON。这时 CPU 数据已在等待插座期间变旧。插座失联还会拖慢健康的 CPU/GPU 数据。两个子命令分别有七秒超时，所以异常情况下整轮等待预算可以接近十四秒，不含终止和调度开销。

修复建议：并行采集不同来源，统一整轮截止时间，输出每项采样时间和有效性。CPU 平均功率与 GPU/插座瞬时值的语义应明确。优先采用单个常驻采集器维护 RAPL 基线和插座连接，以减少每轮 Python、Shell、Go 进程启动与握手。若先保留短进程，也需要防重入、过期数据丢弃和稳定调度。

不要未经验证就认定 Plasma executable 引擎会堆积并发进程；本轮没有核实其调度实现。改造后应针对实际 Plasma 版本观察进程数和刷新间隔。

验收：记录连续输出时间戳，检查间隔分布；让单一来源变慢或断开，健康来源仍能按约定时限更新；没有无限排队或进程数持续增长；晚到旧样本不能覆盖新样本。

## R05：外层超时与后端重试预算冲突

**优先级：P2。审查基线状态：待修复；代码及固定版本依赖源码确认。**

定位：`KDE/backend/read-readings.py:15`；`后端/cmd/xiaomi-power/main.go:167`、`:175`；KDE 内置 Go 副本相同。

采集器固定七秒终止整个子进程组。Go 后端默认每次超时五秒，配置 `WithRetries(1)`；首次握手使用的上下文没有单独总截止时间。检查当前 miio 依赖的握手循环，确认一次失败后还允许一次尝试，因此握手就可能占约十秒。之后还有属性读取阶段。后端配置允许最高六十秒，外层仍固定七秒。

这会使后端独立运行和在组件内运行出现不同结果：第一次握手丢包后，组件可能在重试成功前杀死查询。不能简单放大外层等待，否则会进一步恶化 R04。

修复建议：定义整轮预算，并向握手、重试和属性读取传播剩余截止时间。明确后端独立运行配置与组件运行策略的关系。保留终止整个进程组的行为，避免超时留下子进程。

验收：使用模拟 UDP 设备测试首包丢失、延迟回复、持续丢包；确认在允许预算内可恢复，超时后及时报告不可用；配置不同超时值不会出现隐蔽截断；终止后没有遗留查询进程。

## R06：Android 备份导入仍会整包解压到内存

**优先级：P2。审查基线状态：待修复；依赖源码确认及受控内存复现。**

定位：`后端/xiaomi_power.py:279`；`KDE/backend/xiaomi_power.py` 同步副本。

调用 `AndroidBackup(..., stream=False)` 后，依赖在解密/解压路径中会使用整块 `read()` 和 `BytesIO`。随后 `copyfileobj(..., length=1024*1024)` 只限制复制 SQLite 时的单次缓冲，无法约束此前整个 Android 备份的内存占用。

使用不含真实数据的合成备份验证：压缩数据约 31.9 KiB，归档内容约 32 MiB，通过 `tracemalloc` 观察到 Python 分配峰值约 77.5 MiB。该数值不是 RSS，也不是大文件压力测试，但确认了解压体积与内存占用的关联。

修复建议：采用流式解密、解压和顺序遍历 tar 成员的方式定位数据库；不要在流模式下继续依赖需要随机查找的归档调用。为输入、展开量、目标数据库大小设置合理边界；临时文件仍需限制权限，并在失败、中断后清理。临时盘写满应返回明确错误。

验收：备份体积增加时峰值内存不再按整个归档大小线性增长；压缩、未压缩、加密备份均能处理；不存在目标数据库、文件损坏、过大成员、磁盘满均安全退出，不改坏旧配置。

## R07：安装不是事务式切换，且复制了开发残留

**优先级：P2。审查基线状态：待修复；代码确认，故障注入待实施。**

定位：`KDE/install.sh:58`。

安装器直接把 `backend/.` 复制到当前运行目录，在该目录构建二进制，之后才配置设备、建立链接并升级 KPackage。旧链接指向同一目录时，新脚本会立即被运行中的组件使用。后续构建或包升级失败可能留下新旧版本混杂的安装，没有恢复旧版本的流程。

`cp -R` 不遵守 Git 忽略规则。本地源码安装时，`backend/.venv`、构建产物和 Python 缓存也可能被复制。复制已有虚拟环境还可能保留旧绝对路径；目标中已被源码删除的文件也不会因此消失。在线下载的 GitHub 源码归档通常不含未跟踪文件，这一部分风险主要发生在开发目录安装。

修复建议：仅复制明确允许的源码、依赖清单和运行脚本，在同一文件系统的独立版本目录构建和校验；建立清晰的激活点、互斥锁和回滚路径。虚拟环境在目标版本内创建。后端与前端升级无法天然原子完成时，应记录阶段并能恢复兼容版本。

验收：构建失败、依赖下载失败、扫码取消、KPackage 失败均保留旧版本可用；源码目录放置模拟缓存不会进入安装目录；两个并发安装不会交叉覆盖；升级成功后的文件清单可追踪。

## R08：非空但无效的配置被自动复用

**优先级：P2。审查基线状态：待修复；代码确认。**

定位：`KDE/install.sh:66`；独立后端安装器也存在仅凭文件非空决定复用的路径。

`-s` 只能证明文件存在且长度大于零，不能证明 JSON 有效或字段可用。损坏 JSON、错误结构、空 IP、示例 token 都可能跳过配置并进入“安装完成”，直到运行时才持续显示不可用。KDE 安装流程没有对应的重配选项。

修复建议：先执行不联网的结构与字段校验，检查支持的 model、IP/地址形式、token 格式及超时范围。校验失败时给出中文原因并引导重配；保留旧配置直到新配置安全写入。网络暂时离线与配置格式错误必须分开，不能因短暂离线强迫重新扫码。

验收：缺失、空文件、非法 JSON、数组、缺字段、示例 token 都有可理解的处理；有效配置在插座离线时仍可保留；支持用户主动重新配置；诊断输出不包含 token。

## R09：RAPL 权限依赖同名组，且检查不完整

**优先级：P2。审查基线状态：待修复；代码确认，跨账户实测待补。**

定位：`KDE/setup-rapl-access.sh:115`；`KDE/install.sh:90`。

tmpfiles 规则把用户名同时当作组名。合法桌面账户的主组可能是 `users`，系统不一定存在同名组，因而规则可能无法应用。安装器还在找到任意可读能量文件后就判定无需授权，不能保证实际参与 CPU 统计的所有 Package 都可读。

规则和权限快照使用系统级固定路径，因此多用户场景还需要明确所有权策略：第二个用户重新配置会覆盖规则，而任意一个用户卸载可能撤销另一个用户仍需使用的授权。此场景尚未实机验证。

修复建议：通过 `id -u` 和 `id -g` 获取真实 UID/GID，检查全部目标 Package 和必要字段。保存准确的原权限信息，明确多用户支持范围；若支持多用户，避免反复改变单一属主来表达多个授权。验证重启、驱动重载后的规则是否仍有效。

验收：同名主组、不同名主组、多 Package 部分受限、重复安装均可正确处理；权限恢复可重复执行；不扩大为所有用户可读；多用户行为符合明确文档。

## R10：卸载中途失败与桌面实例残留

**优先级：P2。审查基线状态：待修复；代码确认，真实卸载未执行。**

定位：`KDE/uninstall.sh:33`、`:94`、`:99`。

脚本先删除后端文件，再运行需要管理员授权的 RAPL 恢复。用户取消授权或恢复失败会因 `set -e` 退出，之后的 `--purge-config` 不执行，形成已经卸载一部分、权限及配置仍残留的状态。

组件实例移除只使用 `panelById()`，但配置扫描并未将容器限定为 Panel。若实例位于桌面，查找失败后错误被忽略；另外，未保存到配置文件的实例也未必能从磁盘扫描中找到。应以运行中的 Plasma 实例枚举为优先依据。

修复建议：明确卸载各阶段，尽早处理可能需要授权的工作；非关键步骤失败应汇总报告，并继续独立且已授权的清理。分别处理 Panel 和 Desktop。保存可再次执行的权限恢复入口，避免部分卸载后用户失去恢复工具。

验收：正常卸载、取消提权、没有 qdbus6、Plasma 未运行、桌面实例、多个面板实例及重复卸载均有明确结果；指定 purge 时不能无说明地跳过配置清理；保留不归本安装器管理的命令链接。

## R11：自动同步合并缺少集成验证

**优先级：P2。审查基线状态：待修复；仓库工作流确认，远端配置未知。**

定位：`KDE/.github/workflows/sync-upstream-backend.yml:29`、`:58`。

工作流复制源文件、提交 PR 后请求自动合并，没有在同步内容上构建后端、检查脚本或验证与前端的 JSON 协议。上游编译器版本、字段语义、依赖或配置方式变更都可能引入不兼容。

本轮未查看 GitHub 分支保护和自动合并设置，因此不能断言远端一定立即合并或完全没有保护；已确认的是仓库当前工作流本身没有这些验证步骤。

修复建议：把构建、静态检查、输出字段/错误状态兼容性和关键模拟回归加入必需检查；确认自动创建的 PR 能实际触发并完成检查，再允许合并。记录同步的上游提交，便于回溯。并发同步运行应有明确的防冲突策略。

验收：正常上游更新能自动通过；删除 JSON 必需字段、提高不受支持的 Go 最低版本或引入采集错误时，合并被阻止并能看到原因；检查未启动或失败时不会绕过。

## R12：布局宽度边界与失联抖动

**优先级：P2。审查基线状态：待修复；布局逻辑确认，实际视觉待验证。**

定位：`KDE/package/contents/ui/main.qml:15`、`:159`、`:191`。

CPU/GPU 标签的最小、首选、最大宽度都固定为 `CPU/GPU 888W` 或 `888W` 的度量。GPU 后端却对多张显卡求和，可能出现四位数；大规模多 Package CPU 也存在同类边界。超出空间后的具体裁剪或重叠效果取决于字体和 Qt 渲染，需要实际观察。

另外，全部数据不可用时立即隐藏 CPU/GPU，数据恢复时立即显示，组件宽度随可用性变化。短暂反复失败会推动相邻面板项目。原需求确实要求全部不可用时仅显示总功耗占位，因此应设计短暂故障与持续故障的过渡，而不是简单取消该行为。

修复建议：基于实际显示文本和合理的功耗范围设计宽度，必要时扩大并保持稳定预留；考虑 tabular numbers，但仍使用 Plasma 默认字体。短暂失联保留布局，持续失联再按需求收缩。小面板下的 `Layout.minimumHeight: implicitHeight` 也需实测，不能仅靠静态代码保证不撑高。

验收：深浅主题、HiDPI、不同面板高度、三种模式、CPU/GPU 开关；测试 9/10、99/100、999/1000W、不可用/恢复的切换，无重叠、异常裁剪或频繁跳宽。

## R13：标准 KDE 安装缺少完整运行依赖与提示

**优先级：P2。审查基线状态：待修复；代码与 README 一致确认。**

定位：`KDE/CMakeLists.txt:13`；`KDE/package/contents/ui/main.qml` 的 `readingsCommand`。

CMake 和 ZIP 只安装 Plasmoid 前端。运行命令却固定为 `$HOME/.local/bin/mi-power-monitor-readings`，仅安装标准包不会提供此命令。README 已明确前端包的限制，所以这不是文档谎报整套安装；问题在于前端缺少依赖诊断，用户看到的只是 `--W`。系统级安装的后端也无法自动被这个固定路径发现。

修复建议：明确前端包、系统发行包和一键整合安装的依赖边界；后端命令定位应支持受控的用户级/系统级安装位置。缺少命令时通过原生 tooltip 或简短配置说明引导安装，区分未安装、未配置与设备离线。保持面板简洁，不增加复杂弹窗。

验收：纯前端安装能明确说明缺失依赖；整合安装可直接运行；受支持的系统级安装和 XDG 路径设置下能找到后端；真正离线不被误判为缺少依赖。

## R14：配置写入不是原子操作

**优先级：P2。审查基线状态：待修复；代码确认，故障注入待实施。**

定位：`后端/xiaomi_power.py:258`、`:297` 及扫码保存配置处；KDE 内置副本相同。

各配置入口直接调用 `path.write_text()` 覆盖目标，随后再设为 0600。写入中断、磁盘写满或异常会留下空文件/半截 JSON，并破坏此前可用配置。结合 R08，非空半截文件可能在下次安装时继续被复用。

权限风险需要区分入口：扫码入口提前把目录设为 0700，已有目录的其他入口未统一加固，不能把所有入口都描述成相同的泄漏条件。应让安全权限在内容写入前就生效。

修复建议：统一配置保存函数，在同目录建立 0600 临时文件，完整序列化并校验后刷新数据，再用原子替换切换。按持久性要求处理文件和目录 fsync。异常时删除临时文件、保留旧配置。明确符号链接和并发配置操作的处理。

验收：模拟写入失败、进程中断、替换失败，旧配置始终完整；新文件权限正确；日志无 token；所有配置入口使用相同逻辑，不留下含凭据的临时文件。

## R15：旧版本清理范围过宽且无法回滚

**优先级：P2。审查基线状态：待修复；代码确认。**

定位：`后端/install.sh:135`、`:141`。

激活当前链接后，脚本遍历 `${app_root}/*` 并删除除当前目录以外的所有非隐藏条目。没有验证条目是否由安装器创建、是否属于旧版本，也没有安装清单。用户放在该应用目录中的其他非隐藏内容可能被一并删除。删除范围仍限于应用目录，不能夸大为任意系统文件删除。

旧版本全部删除还意味着新版本运行异常时无法快速回滚；当前成功条件主要是安装步骤完成，并非新版本已经完成可运行性验证。

修复建议：使用受限的版本目录结构和安装标记，只清理明确管理的版本；激活前验证二进制可运行。保留至少一个已知可用版本或提供显式清理策略，兼顾存储占用与恢复能力。不要仅凭目录名字像版本号就删除未知内容。

验收：安装目录中放置未知文件/目录后升级，它们保持不变；新版本验证失败时旧版本仍能启动；连续升级不会无限积累版本；清理不会跟随外部符号链接误删内容。
